## 1. Overview

The liquid inside the glass is not a static model or a pre-baked animation clip. Its surface is a **procedurally animated mesh**: every frame, the height (`y`) of each surface vertex is recomputed from a closed-form mathematical model and pushed into the mesh. No animation library, physics engine, or asset drives it — the motion is generated entirely by our own code from a handful of scalar parameters and the current time.

The headline effect is the **ripple field**: when a coin strikes the liquid, a circular wave radiates outward from the surface, grows shallower as it spreads, and fades over time. Crucially, several ripples can be alive at once and **add together** (linear superposition), so rings from rapid coin drops interfere — reinforcing where two crests meet and cancelling where a crest meets a trough — exactly like real water.

## 2. Why this is an "automatic procedure"

It satisfies the requirement on every point:

- **Automatic** — it runs every frame with no manual input; it reacts to game events (coin impacts) but the motion itself is generated by the procedure.
- **Self-implemented** — the wave model, the time-decay envelope, the superposition sum, and the per-vertex update loop are all written by us. The only external calls are scalar math primitives (`sin`, `exp`), which are language-level functions, not a graphics/animation library. No tween library, no Unity `Animation`/`Animator`, no particle or fluid package.
- **Graphics-relevant** — it is a procedural-geometry technique: a parametric surface deformed per-vertex, a core Theory-of-Computer-Graphics topic.

## 3. Mathematical formulation

### 3.1 Domain

The liquid surface is a disc of vertices generated procedurally in `LiquidBodyMesh.Build`. Each surface vertex `i` has a normalised radius

$$r_i \in [0, 1]$$

measured from the centre of the surface to the rim. Time is `t` (seconds). The surface base height is `y_0` (the calm liquid level, which itself rises with the in-game overflow risk).

### 3.2 A single ripple

One coin impact spawns a **damped, radially-travelling sine wave**. Its contribution to the height at radius `r` and time `t` is

$$
w(r, t) \;=\; \underbrace{A\,e^{-d\,\tau}}_{\text{time decay (envelope)}}
\;\cdot\;
\underbrace{\sin\!\big(k\,r \;-\; v\,\tau\big)}_{\text{travelling wave}}
\;\cdot\;
\underbrace{(1 - 0.15\,r)}_{\text{radial falloff}}
$$

where

| Symbol | Meaning | Field / value |
|---|---|---|
| `A` | initial amplitude (crest height) | `rippleAmplitude` × kick strength |
| `τ = t − t₀` | age of the wave (`t₀` = impact time) | per-wave |
| `d` | temporal decay rate | `rippleDecay` (1.9) |
| `k` | wavenumber (rings per unit radius) | `rippleWavelength` (22) |
| `v` | angular phase speed (outward travel) | `rippleSpeed` (9) |

- The **travelling-wave** term `sin(kr − vτ)` is the heart of it. Holding `t` fixed and varying `r` gives concentric rings; holding `r` fixed and advancing `t` makes the phase decrease, so the rings appear to move *outward* over time.
- The **envelope** `A·e^(−dτ)` is exponential decay: the wave starts at amplitude `A` and dies smoothly, so a ripple fades instead of ringing forever.
- The **radial falloff** `(1 − 0.15r)` keeps the rim slightly calmer than the centre.

### 3.3 Superposition (the key upgrade)

Real water obeys the superposition principle: independent disturbances add. We model exactly that. With up to `N` live ripples (each with its own age `τⱼ` and amplitude `Aⱼ`), the total ripple height at a vertex is the **sum**

$$
W(r, t) \;=\; \sum_{j=1}^{N} A_j\,e^{-d\,\tau_j}\,\sin\!\big(k\,r - v\,\tau_j\big)\,(1 - 0.15\,r)
$$

Because each wave carries a different age `τⱼ`, the waves are at different phases at the same radius — so they **interfere**. Two crests reinforce (constructive); a crest over a trough cancels (destructive). This is what makes overlapping rings from quick successive coin drops look believable rather than a single ring being replaced.

### 3.4 The full surface height

The ripple is one of several additive terms composing the final vertex height. The complete per-vertex model is

$$
y(r, t) \;=\; y_0 \;+\; \text{concave}(r) \;+\; \text{dome}(r) \;+\; \text{tremble}(r,t) \;+\; \text{ambient}(r,t) \;+\; W(r,t) \;+\; \text{slosh} \;+\; \text{spill}
$$

These layers are all procedural; this report focuses on the **ripple field `W`** as the assessed automatic procedure (the others — meniscus curvature, danger dome, micro-wobble — are supporting effects built the same way).

## 4. Implementation

### 4.1 Spawning a wave (`KickRipple`)

Each coin impact calls `KickRipple(strength)`. Instead of overwriting the previous ripple, it writes a new `RippleWave { StartTime, Amplitude }` into a small fixed-size **round-robin buffer** (`MaxConcurrentRipples = 6`). When the buffer is full, the oldest (and therefore faintest) wave is overwritten. This bounds cost to a constant and needs no allocation at runtime.

```csharp
public void KickRipple(float strength)
{
    rippleWaves[nextRippleSlot] = new RippleWave
    {
        StartTime = Time.time,
        Amplitude = rippleAmplitude * Mathf.Max(0f, strength)
    };
    nextRippleSlot = (nextRippleSlot + 1) % rippleWaves.Length;
}
```

### 4.2 Per-frame evaluation (`UpdateSurfaceVertices`)

Each frame the procedure runs in two stages for efficiency:

1. **Precompute** (once per frame, outside the vertex loop): for every live wave, cache its age `τⱼ` and its time-decayed amplitude `Aⱼ·e^(−dτⱼ)`. The expensive `exp` is therefore evaluated `N` times per frame, not once per vertex.

2. **Per-vertex sum** (inside the loop over surface vertices): evaluate only the cheap spatial term `sin(kr − vτⱼ)` and accumulate the superposition `W`. Waves whose decayed amplitude has fallen below a small threshold are skipped.

```csharp
var ripple = 0f;
var rippleFalloff = Mathf.Clamp01(1f - r * 0.15f);
for (var k = 0; k < rippleWaves.Length; k++)
{
    if (rippleEnvelopeScratch[k] <= 0.0001f)
        continue;

    ripple += Mathf.Sin(r * rippleWavelength - rippleElapsedScratch[k] * rippleSpeed)
        * rippleEnvelopeScratch[k] * rippleFalloff;
}
```

The summed heights are written back to the mesh and normals are recomputed so lighting follows the deformation:

```csharp
waterMesh.vertices = workingVertices;
waterMesh.RecalculateNormals();
waterMesh.RecalculateBounds();
```

### 4.3 Sampling adequacy (Nyquist)

A travelling wave can only be displayed smoothly if the mesh has enough rings to resolve it. `GlassVisualController` therefore tessellates the surface to roughly **6 rings per ripple wavelength** across the radius — comfortably above the Nyquist minimum of 2 samples/cycle — so a short wavelength stays smooth regardless of the authored ring count. This is a direct application of the sampling theorem to procedural geometry.

## 5. Parameters and tuning

All wave behaviour is controlled by the inspector-exposed scalars under **Surface Motion**:

| Parameter | Effect of increasing it |
|---|---|
| `rippleAmplitude` | taller initial ripple |
| `rippleWavelength` (`k`) | more, tighter rings |
| `rippleSpeed` (`v`) | rings travel outward faster |
| `rippleDecay` (`d`) | ripple fades sooner |
| `MaxConcurrentRipples` | how many waves can interfere at once |

Changing any value changes the look without touching the algorithm — the hallmark of a parametric procedural method.

## 6. Validation

- **Compiles** cleanly (Unity bundled Roslyn, `Meniscus.Runtime` assembly — no errors/warnings).
- **Visual check (in-engine):** dropping several coins in quick succession produces overlapping rings that visibly interfere, then decay; a single drop produces one clean expanding ring that fades.
- **Boundary behaviour:** before any impact (and in the editor at `t = 0`) all amplitudes are zero, so `W = 0` and the surface is calm — the rest pose is well-defined.

## 7. Summary

The water surface is animated by a fully self-implemented procedure: a sum of damped, radially-travelling sine waves evaluated per vertex per frame, with linear superposition producing physically-plausible interference. It uses only scalar math primitives, is driven entirely by game time and a few parameters, and is a textbook procedural-geometry / object-movement technique — meeting the assignment's "one automatic procedure, self-implemented without a library" requirement.
